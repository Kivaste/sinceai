# Names and taglines

Limits: name <= 80 characters, tagline <= 140 characters (read first by voters). Counts include spaces.
Content-free. Say "pseudonymised", never "anonymised"; claim only what a named check proves.

## Project name options

| # | Name | Chars | Angle |
|---|---|---|---|
| N1 | Purpose-First PETs: share only what's needed, and prove it | 58 | Says the approach (purpose first) and the promise (proof). Matches the glossary title. |
| N2 | pets-release: a data release that proves its own privacy | 56 | Names the tool and its differentiator (the manifest). Best for the repo and the CLI. |
| N3 | Say False: privacy manifests that can only say false | 52 | Memorable hook; explains less on its own. |

**Recommendation: N1.** A voter sees the idea without context, and the CLI name `pets-release` still appears under "Built with".

## Tagline options

| # | Tagline | Chars | Angle |
|---|---|---|---|
| T1 | Give a recipient only the data their purpose needs, then prove what was removed with checks anyone can re-run offline. | 118 | Purpose first, then proof. Plain. |
| T2 | Release only what the purpose needs. A fail-closed gate refuses leaks; a signed manifest names the check behind every claim. | 124 | Names the two mechanisms (gate, manifest). |
| T3 | Offline PETs tool: it builds the release, refuses it on any leak, and ships a manifest whose claims you can re-verify yourself. | 127 | Process order; stresses offline and re-verify. |
| T4 | Not 'trust us, it's anonymised': a release plus a manifest where every privacy claim is a named check you can re-run. | 117 | Contrasts with the usual claim; honest about anonymisation. |
| T5 | From data request to protected release in one offline command, with measured privacy, measured utility and proof attached. | 122 | Product-first, stresses the one command and the numbers. |

**Recommendation: T1** for first-time voters (no jargon, states both halves). Use T4 in the pitch as the spoken contrast line.
